- **Python & Environment**: Python 3.12.
  - On Windows, run consumers and tests with a **NON-venv base Python 3.12 interpreter**.
  - Install dependencies directly into the base interpreter:
    ```bash
    python -m pip install -r requirements.txt
    ```

    1. Both the repo virtual environment and a fresh virtual environment built strictly from `requirements.txt` failed on Windows (PySpark workers crashed on launch with `java.io.EOFException`, even on a trivial pandas UDF).
    2. The base system interpreter with identical pinned versions passed all isolated tests and the live demo.
    3. Package versions alone do not explain the failure; virtualenvs failed in our tests on Windows; Linux/WSL/Docker are untested by us.
    4. The root cause remains UNVERIFIED.
  - Downstream Member 4 inference readers using pure Python Kafka consumers (`kafka-python`) do not use PySpark workers and run under either environment.
- **PySpark**: PySpark 4.1.1 (matching `member2_spark` and `member3_streaming`).
- **Kafka Client**: `kafka-python` or `confluent-kafka` (`kafka-python` is specified in `requirements.txt`).

## 3. 10-Minute Quickstart

Run these exact commands from the repository root to start the stream and see live features arriving:

### Step 1: Start Kafka Broker
```bash
docker compose -f member3_streaming/docker-compose.yml up -d
```
Verify the container is healthy:
```bash
docker ps
```

### Step 2: Create Kafka Topics
```bash
python member3_streaming/create_topics.py
```
This provisions all six topics (`financial_transactions_paysim`, `financial_features_paysim`, `financial_transactions_paysim_dlq`, `financial_transactions_ieee`, `financial_features_ieee`, `financial_transactions_ieee_dlq`) with partition count 1 and 7-day retention.

### Step 3: Run Producer (Produce 1,000 Transactions)
In Terminal 1, produce 1,000 transactions at 50 ms delay:
```bash
python -m member3_streaming.producer_paysim --limit 1000 --delay 0.05
```

### Step 4: Run Feature Consumer
In Terminal 2, start the streaming feature pipeline (single line):
```bash
python -m member3_streaming.consumer_paysim --bootstrap-servers localhost:9092 --input-topic financial_transactions_paysim --output-topic financial_features_paysim --dlq-topic financial_transactions_paysim_dlq --checkpoint-location member3_streaming/checkpoints/paysim_quickstart
```

*PowerShell multi-line variant:*
```powershell
python -m member3_streaming.consumer_paysim `
    --bootstrap-servers localhost:9092 `
    --input-topic financial_transactions_paysim `
    --output-topic financial_features_paysim `
    --dlq-topic financial_transactions_paysim_dlq `
    --checkpoint-location member3_streaming/checkpoints/paysim_quickstart
```

### Step 5: Read and Deduplicate Features
In Terminal 3, run Member 3's reference deduplicating reader:
```bash
python member3_streaming/example_consumer_member4.py
```
The example consumer deduplicates on `txn_id` and prints summary fields (`txn_id`, simulation `step`, and `amount`) for the first 10 records.

To print a full 42-column record as formatted JSON in a single command, run:
```bash
python -c "import json, kafka; c = kafka.KafkaConsumer('financial_features_paysim', bootstrap_servers=['localhost:9092'], auto_offset_reset='earliest', consumer_timeout_ms=5000); msg = next(c); rec = json.loads(msg.value.decode('utf-8')); print(f'Total columns: {len(rec)}'); print(json.dumps(rec, indent=2)); c.close()"
```

## 4. The Columns: Field Semantics & Best Practices

### 4.1 Primary Keys (Deduplication Anchors)
- **PaySim**: `txn_id` (deterministic SHA-256 hex string generated from `step|type|amount|nameOrig|nameDest`).
- **IEEE-CIS**: `TransactionID` (32-bit integer).
- **Rule**: These are unique record identifiers. Never include them as numerical model features!

### 4.2 Target Label: `isFraud`
- `isFraud` is present in both stream outputs (0 = legitimate, 1 = fraudulent).
- **CRITICAL**: `isFraud` is the ground-truth target. It is **NEVER A MODEL INPUT**. You must drop `isFraud` from your feature matrix $X$ before passing records to model inference (`model.predict_proba(X)`).

### 4.3 Data Split: `split`
- **PaySim**: Has 3 deterministic temporal partitions:
  - `'train'`: simulation `step <= 500` (~first 21 days)
  - `'valid'`: simulation `501 <= step <= 600` (~days 21 to 25)
  - `'test'`: simulation `601 <= step <= 743` (~days 25 to 31)
- **IEEE-CIS**: Has 2 temporal partitions:
  - `'train'` and `'valid'` (derived from transaction timeline; test split is reserved for unlabelled submission).
- **Rule**: **NEVER perform a random train/test split (e.g. `train_test_split(shuffle=True)`)**. You must split strictly along temporal boundaries using the `split` column to prevent catastrophic forward-looking temporal leakage.

### 4.4 Categorical Features & Raw Strings
- **PaySim**: `type` is present as a string (`TRANSFER`, `CASH_OUT`, `PAYMENT`, `CASH_IN`, `DEBIT`). Member 3 also provides one-hot columns: `type_transfer`, `type_cash_out`, `type_payment`, `type_cash_in`, `type_debit`.
- **IEEE-CIS**: Categoricals include `ProductCD`, `card4`, `card6`, `P_emaildomain`, `R_emaildomain`, and `M1` through `M9`. Missing values are mapped to `'missing'`.

### 4.5 Null Semantics & Real Missingness
- **PaySim**: First-seen destinations legitimately have `null` for prior aggregates (`dest_prior_amount_mean`, `dest_prior_amount_std`, `dest_steps_since_last_txn`, `dest_amount_zscore`, `dest_prior_cashout_share`). For single-transaction histories (`count == 1`), sample standard deviation and Z-score are `null`.
- **IEEE-CIS**: Each transaction row has approximately **~234 null values out of 483 columns**. This is real domain missingness reflecting transaction channel diversity (e.g. credit vs debit, desktop vs mobile web, card-present vs eCommerce).
- **Handling**: Use gradient boosted decision trees (such as XGBoost, LightGBM, or CatBoost) which handle sparse null values natively without requiring artificial imputation.

### 4.6 Feature Version
- Both topics output `feature_version = "v1.0"` for schema lineage tracking.

## 5. Mandatory Rules You Must Follow

1. **Deduplicate on Primary Key**: Spark Structured Streaming guarantees **at-least-once** delivery. In the event of a worker or driver restart, duplicate messages may be emitted. Duplicates are byte-identical. Your scoring consumer must deduplicate using `seen_keys = set()` or a Redis/RocksDB filter.
2. **Preserve Time Ordering**: Time-ordered arrival is expected. Events arriving out of order are routed to the DLQ as `LATE_EVENT`.
3. **No Random Splits**: Train strictly using the `split` column.
4. **No Post-Transaction Balances**: PaySim balance columns `newbalanceOrig` and `newbalanceDest` (Tier B) were intentionally removed from the pipeline because they leak the transaction outcome.
5. **Exact Match with Batch Features**: The streaming feature columns match Member 2's batch Parquet schema with $10^{-6}$ precision. A model trained on Member 2's `paysim_features.parquet` or `ieee_features.parquet` will score the real-time stream without retraining or schema adaptation.

## 6. Suggested Path for Member 4

*(Clearly labelled as a suggested implementation path)*

1. **Train Offline Models on Member 2 Parquet**:
   - Load `data/features/paysim_features.parquet` and `data/features/ieee_features.parquet`.
   - Filter `split == 'train'` for fitting and `split == 'valid'` for validation / hyperparameter tuning.
   - Drop identifiers (`txn_id`, `nameOrig`, `nameDest`, `TransactionID`) and target (`isFraud`).
2. **Manage Imbalance & Evaluate Metrics**:
   - Both datasets suffer from severe class imbalance (~0.13% fraud in PaySim, ~3.5% in IEEE).
   - Do NOT optimize for accuracy. Use Precision, Recall, PR-AUC, and ROC-AUC.
   - Tune classification thresholds based on business cost matrix (cost of false positive friction vs cost of missed fraud loss).
3. **Wrap Inference in a Real-Time Consumer**:
   - Subscribe to `financial_features_paysim` or `financial_features_ieee`.
   - Deduplicate on `txn_id` or `TransactionID`.
   - Pass row features into `model.predict_proba(X)[:, 1]`.
4. **Publish Scores to Downstream Topics for Member 5**:
   - We propose publishing model scores to:
     - `fraud_scores_paysim`
     - `fraud_scores_ieee`
   - Suggested scoring payload schema:
     ```json
     {
       "txn_id": "8f8b8...",
       "fraud_score": 0.8421,
       "model_version": "xgb_v1.0",
       "scored_at": "2026-10-18T03:30:00.000000Z"
     }
     ```

## 7. Crash Behavior and Known Issues

*(Worded identically to the Member 3 contracts)*

- **IEEE-CIS Stateful Crash Recovery (Restart-Twice, No File Edits)**:
  - After a hard crash mid-batch, restart the consumer; the first restart completes the interrupted batch and then exits non-zero with the Spark 4.1.1 `KafkaMicroBatchStream.metrics` NPE; restart it again and it continues normally. No file edits.
  - Evidence: `git show member3-evidence-archive:member3_streaming/reports/raw/PDG_restart_twice.txt` (IEEE stateful, one run, kill at 2,123, 412 byte-identical duplicates, 0 missing, 0 stateful mismatches).
  - Unattended recovery requires a process supervisor that restarts the process on a non-zero exit; this was not built or tested.
- **PaySim Stateful Crash Recovery (Documented Operator Workaround)**:
  - If a hard crash occurs mid-batch on PaySim, delete the orphan uncommitted `offsets/N` and `offsets/.N.crc` (where `commits/N` does not exist), and restart. Never delete files in `commits/`. PaySim restart-twice is untested.
- **Micro-Batch Reordering**:
  - Events arriving within a single micro-batch are sorted ascending by timestamp/step inside the state function, meaning intra-batch out-of-order events are absorbed and reordered, not rejected as `LATE_EVENT`.
- **Windows Test Suite Flakiness**:
  - Even with the pinned environment, the streaming tests are occasionally flaky on Windows (BlockManager NPE); run them one at a time with `python member3_streaming/run_slow_tests_isolated.py`.
